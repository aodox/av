## 一、多租户架构模式概述

根据2025-2026年SaaS行业最佳实践，多租户架构主要有三种模式：

### 1.1 Pooled 模式（共享一切）

```
┌─────────────────────────────────────────────────────┐
│                    应用服务器                        │
│              (所有租户共享)                          │
└───────────────────────┬─────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────┐
│                    共享数据库                        │
│     ┌─────────────────────────────────────────┐     │
│     │  tenant_id │ uid │ data │ created_at   │     │
│     ├────────────┼─────┼──────┼──────────────┤     │
│     │  tenant_A  │ 001 │ ...  │ 2026-05-11   │     │
│     │  tenant_B  │ 001 │ ...  │ 2026-05-11   │     │
│     │  tenant_A  │ 002 │ ...  │ 2026-05-11   │     │
│     └─────────────────────────────────────────┘     │
└─────────────────────────────────────────────────────┘
```

**特点**：
- 所有租户共享同一数据库和表
- 通过 `tenant_id` 列区分数据
- 依赖应用层或数据库RLS（行级安全）实现隔离

**适用场景**：
- 10,000+ 租户
- 成本敏感型产品
- 无严格合规要求
- 早期MVP产品

**优点**：
- 成本最低
- 运维简单
- 易于扩展租户数量

**缺点**：
- 数据隔离依赖应用层
- 单租户问题可能影响全局
- 不满足某些合规要求（如数据驻留）

---

### 1.2 Bridge 模式（共享计算，隔离数据）

```
┌─────────────────────────────────────────────────────┐
│                    应用服务器                        │
│              (所有租户共享)                          │
└───────────────────────┬─────────────────────────────┘
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
┌───────────────┐ ┌───────────────┐ ┌───────────────┐
│  Tenant A DB  │ │  Tenant B DB  │ │  Tenant C DB  │
│   (独立库)    │ │   (独立库)    │ │   (独立库)    │
└───────────────┘ └───────────────┘ └───────────────┘
```

**特点**：
- 共享应用层计算资源
- 每个租户独立数据库（或独立Schema）
- 连接路由在应用层实现

**适用场景**：
- B2B SaaS
- 数据驻留要求（如GDPR）
- 中等规模租户（100-10,000）
- 需要租户级备份恢复

**优点**：
- 数据隔离更强
- 支持租户级备份
- 满足部分合规要求

**缺点**：
- 运维复杂度增加
- 成本高于Pooled模式
- 连接池管理复杂

---

### 1.3 Silo 模式（完全隔离）

```
┌─────────────────┐   ┌─────────────────┐   ┌─────────────────┐
│   Tenant A      │   │   Tenant B      │   │   Tenant C      │
│  ┌───────────┐  │   │  ┌───────────┐  │   │  ┌───────────┐  │
│  │  App Server│  │   │  │  App Server│  │   │  │  App Server│  │
│  └─────┬─────┘  │   │  └─────┬─────┘  │   │  └─────┬─────┘  │
│        │        │   │        │        │   │        │        │
│  ┌─────▼─────┐  │   │  ┌─────▼─────┐  │   │  ┌─────▼─────┐  │
│  │  Database │  │   │  │  Database │  │   │  │  Database │  │
│  └───────────┘  │   │  └───────────┘  │   │  └───────────┘  │
└─────────────────┘   └─────────────────┘   └─────────────────┘
     独立账户              独立账户              独立账户
```

**特点**：
- 每个租户完全独立的基础设施
- 可能是独立的云账户/VPC
- 最高级别的隔离

**适用场景**：
- 企业级客户
- 严格合规要求（HIPAA, FedRAMP, SOC2）
- 大客户定制需求
- 金融/医疗/政府行业

**优点**：
- 最高安全级别
- 完全满足合规要求
- 支持深度定制
- 单租户问题不影响其他租户

**缺点**：
- 成本最高
- 运维最复杂
- 扩展租户需要部署新环境

## 二、模式选择决策框架

### 2.1 决策树

```
                    ┌─────────────────────────┐
                    │ 是否有严格合规要求？      │
                    │ (HIPAA/FedRAMP/数据驻留) │
                    └───────────┬─────────────┘
                                │
                    ┌───────────┴───────────┐
                    │                       │
                   是                       否
                    │                       │
                    ▼                       ▼
            ┌───────────────┐       ┌───────────────────┐
            │ Silo 或 Bridge │       │ 租户数量是多少？   │
            └───────────────┘       └─────────┬─────────┘
                                              │
                                  ┌───────────┴───────────┐
                                  │                       │
                              <1000                    >1000
                                  │                       │
                                  ▼                       ▼
                          ┌───────────────┐       ┌───────────────┐
                          │ Bridge 模式   │       │ Pooled 模式   │
                          └───────────────┘       └───────────────┘
```

### 2.2 对比表

| 维度 | Pooled | Bridge | Silo |
|------|--------|--------|------|
| **成本** | 💰 最低 | 💰💰 中等 | 💰💰💰 最高 |
| **数据隔离** | 应用层 | 数据库级 | 基础设施级 |
| **运维复杂度** | ⭐ 简单 | ⭐⭐ 中等 | ⭐⭐⭐ 复杂 |
| **扩展性** | ✅ 优秀 | ⚠️ 一般 | ❌ 困难 |
| **定制能力** | ❌ 有限 | ⚠️ 部分 | ✅ 完全 |
| **合规满足** | ❌ 基础 | ⚠️ 部分 | ✅ 完全 |
| **典型租户数** | 10K+ | 100-10K | <100 |

## 三、本项目架构分析

### 3.1 当前采用模式

**本项目采用 Pooled 模式**，具体实现：

```
┌─────────────────────────────────────────────────────────────┐
│                    Gin HTTP Server                          │
│                   (高并发 HTTP 处理)                         │
└───────────────────────────┬─────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                     Service Layer                            │
│         (通过 app_id 参数实现租户隔离)                        │
└───────────────────────────┬─────────────────────────────────┘
                            │
            ┌───────────────┴───────────────┐
            ▼                               ▼
┌─────────────────────────┐     ┌─────────────────────────┐
│         Redis           │     │        MySQL            │
│   Key: {app_id}:{uid}   │     │   WHERE app_id = ?      │
└─────────────────────────┘     └─────────────────────────┘
```

### 3.2 多租户隔离实现

#### 数据模型

```go
type Stream struct {
    ID       int64  `gorm:"primaryKey"`
    AppID    string `gorm:"index:idx_app_uid_status,priority:1"` // 租户标识
    UID      int64  `gorm:"index:idx_app_uid_status,priority:2"` // 用户ID
    Status   int    `gorm:"index:idx_app_uid_status,priority:3"` // 状态
    // ...
}
```

#### 缓存键设计

```
stream:{stream_id}           → 流详情
active_streams:{app_id}:{uid} → 活跃流ID
```

#### 数据库查询

所有查询强制包含 `app_id` 条件：

```sql
-- 安全查询
SELECT * FROM streams WHERE app_id = ? AND uid = ? AND status = 1;

-- 不安全查询（已弃用）
SELECT * FROM streams WHERE uid = ? AND status = 1;  -- ❌ 跨租户风险
```

### 3.3 索引优化

创建复合索引优化多租户查询：

```sql
CREATE INDEX idx_app_uid_status ON streams (app_id, uid, status);
```

**查询优化效果**：

| 查询场景 | 无索引 | 有复合索引 |
|---------|--------|-----------|
| 查询某租户某用户的活跃流 | 全表扫描 | 索引命中 |
| 查询某租户所有活跃流 | 部分扫描 | 索引前缀命中 |
| 统计某租户流数量 | 全表扫描 | 索引覆盖 |

## 四、最佳实践

### 4.1 接口设计

**所有接口都应传递 `app_id`**：

```bash
# ✅ 推荐
GET /api/v1/stream/status?app_id=customer_001&uid=10001

# ⚠️ 不推荐（使用默认租户）
GET /api/v1/stream/status?uid=10001
```

### 4.2 数据库层隔离

**PostgreSQL RLS（推荐升级路径）**：

```sql
-- 启用行级安全
ALTER TABLE streams ENABLE ROW LEVEL SECURITY;

-- 创建策略
CREATE POLICY tenant_isolation ON streams
    USING (app_id = current_setting('app.tenant_id'));

-- 强制所有用户（包括表所有者）
ALTER TABLE streams FORCE ROW LEVEL SECURITY;
```

### 4.3 租户上下文中间件

```go
func TenantMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        // 从多种来源提取租户ID
        tenantID := c.GetHeader("X-Tenant-ID")
        if tenantID == "" {
            tenantID = c.Query("app_id")
        }
        if tenantID == "" {
            // 从JWT提取
            if claims, ok := c.Get("jwt_claims"); ok {
                tenantID = claims.(JWTClaims).TenantID
            }
        }
        if tenantID == "" {
            tenantID = "default"
        }
        
        c.Set("tenant_id", tenantID)
        c.Next()
    }
}
```

### 4.4 审计日志

所有敏感操作记录租户上下文：

```go
logger.Infof("[AUDIT] action=%s, tenant=%s, uid=%d, ip=%s",
    action, appID, uid, clientIP)
```
